# Federated Contribution Authoring

Contribution teams own source repositories, tests, release history, and internal npm publication. The platform team owns catalog acceptance and Web Doctor release assembly. Publishing a package makes it available for review; it does not register or activate the contribution.

## Start from a Template

The package ships policy templates for firmwide, portal, platform, and application layers under `templates/`. It also ships an ESLint plugin template. Replace example identifiers, owners, compatibility ranges, provenance, Controls, and fixtures before publication.

Validate a policy pack with its provider catalog and pass/fail fixtures:

```sh
web-doctor policy validate --policy templates/firmwide/policy.json --provider templates/eslint-plugin/provider.json --fixture templates/policy-accept.fixture.json --fixture templates/policy-reject.fixture.json --json
```

Validate an ESLint provider manifest, contribution metadata, plugin rule catalog, and deterministic fixtures:

```sh
web-doctor provider validate --manifest templates/eslint-plugin/provider.json --contribution templates/eslint-plugin/web-doctor.json --plugin templates/eslint-plugin/plugin.mjs --fixture templates/eslint-plugin/fixtures/pass.json --fixture templates/eslint-plugin/fixtures/fail.json --json
```

## Validate and Publish

Create a canonical tarball in temporary staging. This command validates documents, fixture expectations, runtime digests, and source provenance without changing author files:

```sh
web-doctor contribution pack --root templates/firmwide --output tmp/contribution-pack --json
```

Publish the resulting immutable tarball through the team's existing internal npm workflow. Use a new exact version for every byte change. Never overwrite or unpublish a version used by a catalog or historical Web Doctor release.

## Propose Catalog Acceptance

After publication, team CI runs `web-doctor contribution propose` with the package identity, provenance, registry, and catalog paths. The output path must be separate from the reviewed catalog. The command resolves registry-reported SHA-512 integrity and writes a canonical candidate.

Team CI opens a pull request containing the candidate catalog change. The pull request must also include the regenerated lock. Publishing credentials cannot merge that pull request or bypass platform CODEOWNERS, branch protection, fixture validation, integrity checks, or provenance review.

## Platform Review and Embedding

Platform reviewers verify ownership, namespace, compatibility, capabilities, dependencies, fixtures, false-positive evidence, resource bounds, package integrity, and source provenance. Registry CI retrieves the exact package with lifecycle scripts disabled and rejects lock drift or undeclared content.

After approval and merge, release CI retrieves the same exact package and rebuilds the lock and embedded snapshot. It compares all generated bytes with reviewed Git state. The Web Doctor package embeds accepted documents and runtime artifacts. Applications install only the approved Web Doctor package; they do not fetch contribution packages.

## Retirement and Rollback

Deprecation and retirement are reviewed catalog changes with migration guidance and an optional active replacement. Retained package versions remain immutable for audit and reproduction. Rollback selects a retained exact contribution or Web Doctor version through a new reviewed change; it never mutates published bytes.
